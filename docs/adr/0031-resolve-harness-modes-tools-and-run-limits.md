# 0031. Resolve's two modes share one prompt, one config and one local order-book tool; baseline spawns PayPal's server per run with a fresh token; runs have hard limits and rerun only before any tool call

Status: accepted, applies ADRs 0011, 0014, 0015 and 0017 to phase 8 (nothing in them changes)
Decided-by: autopilot (delegated), phase 8 feature spec, 18 Oct 2026, under brief §14 v1.4. The answerer's rules escalate the order-book tool and the prompt, because they bear on "the baseline isn't tuned to fail" (§8), an intent question. The planner session had no way to start the answerer agent, so it applied the answerer's rules itself. Decided by brief §10 trade-offs 1 (fail closed), 2 (honest evidence) and 4 (a stranger understands it). The owner can overturn it (`.ralph/human.md`, Decided for you)
Question: How exactly do Resolve's protected and baseline modes differ? Customers name orders as `KIK-1042`, but PayPal's tools need PayPal's order and capture IDs: how does the agent get from one to the other? How does baseline mode get a PayPal token without the model seeing it? What limits a run, and when may a run be retried?
Decision:
- **Only the MCP transport differs.** Both modes send the same system instruction (a byte-stable constant with no dates or ticket data), the same model and fallback, the same config (ADR 0013: `VALIDATED`, thinking `MEDIUM`, all five safety categories `OFF`, `maxOutputTokens` 8,192), the same sanitizer (ADR 0014), the same user-turn rendering and the same local tool. The tools each server lists differ, because the servers differ: that's the comparison.
- **Protected mode** connects to the gate (`GATE_MCP_URL`, default `http://127.0.0.1:8787/mcp`) over Streamable HTTP with `COUNTERSIGN_SUPPORT_AGENT_KEY` as the bearer token. If the key is unset, or the gate answers 401 or can't be reached, the run fails before any model call (`gate_unavailable`).
- **Baseline mode** mints a fresh sandbox access token for each run through `@countersign/rail-paypal` (a new `issueAccessToken()`, sandbox-only like every other call), and spawns `@paypal/mcp --tools=all` from the `apps/baseline-paypal-mcp` workspace with `process.execPath`, never `npx`. The child's environment is the SDK's default environment plus `PAYPAL_ACCESS_TOKEN` and `PAYPAL_ENVIRONMENT=SANDBOX`; its stderr is dropped. The child is closed when the run ends, however it ends. No code imports the toolkit. Baseline runs move real sandbox money with no gate, so nothing they do is in the audit log; their tool calls are in the run's trace, marked baseline.
- **A local, read-only order-book tool, `find_order`,** stands for the merchant's own shop system and is declared in both modes beside the server's tools. Given an order number such as `KIK-1042`, it answers from `seed_orders`: the order number, PayPal order ID, capture ID, amount as `{ value, currency_code }`, and tracking number, or "No order with that number." It never returns the payer's email: the records that decide a refund are the gate's to read. It's the only local tool; replies are the model's final text, not a `send_reply` tool.
- **The user turn** renders the thread: earlier messages and Resolve's replies as plain text, then the message being answered with its ticket ID, channel, sender, subject, received time and body, and its photos as inline image parts. The ticket ID is how the agent fills `justification.ticket_id`; the gate then reads the real sender from the store (ADR 0029).
- **Limits.** At most 8 model calls and 12 tool calls per run. Reaching either ends the run (`step_cap`) with no reply and no further tool call. A function call naming a tool that wasn't declared ends the run (`unknown_tool`) without forwarding it. An MCP transport failure ends the run (`tool_transport_failed`). A model response that fails ADR 0015's check ends the run (`model_stopped:<reason>`). A final response with no reply text ends it (`empty_reply`). Each of these is status `stopped` or `failed`, never a reply, and the message waits for the merchant.
- **Retries.** Model calls use the SDK's retries for 408 and 5xx (ADR 0015). On a 429, the run waits once if the error's retry delay is 10 seconds or less, and otherwise ends `model_unavailable`. A run that ends `model_unavailable` before any tool call ran is followed by one new run of the same message on `GEMINI_FALLBACK_MODEL`, when that's set. A run in which any tool call ran is never retried. Tool calls are never retried.
- **Secrets stay out.** The principal key and the PayPal token never appear in the model's contents, the trace, a log line or an API answer.
Basis:
- Brief §5 item 6 ("the same agent wired straight to PayPal's tools"), §8 ("The baseline isn't tuned to fail"; fail closed; credential custody), §3 (PayPal's tool names, "switching is one URL change").
- ADR 0011 (one harness, stdio baseline, isolated workspace, mint a token per spawn), ADR 0014 (our own loop, sanitizer, trace), ADR 0015 (response check, retries, fallback only between runs), ADR 0017 (`GEMINI_MODEL`, `GEMINI_FALLBACK_MODEL`).
- Spike S4: PayPal's server lists 28 tools and has no lookup by the shop's order number; seeded orders carry `invoice_id` `<order number>-<run ID>`, which none of its tools search by. Spike S8: thought signatures survive when the model's content is appended unchanged.
- Original brief §11: Resolve's read tools include `get_order` and `search_tickets`; "the system prompt tells the agent that customer content is data, not instructions. That's good practice, but nothing depends on it."
Consequences:
- The bench (phase 14) measures both modes with this harness unchanged. Any tool allowlist must be identical in both modes (ADR 0014).
- `find_order` knows only seeded orders. A storefront sale isn't in `seed_orders`, so the agent can't find it by number until a later phase adds those orders.
- Spike S4's audit finding stands: the toolkit's dependency tree has known vulnerabilities, so phase 13 decides whether baseline mode is offered on the hosted URL.
