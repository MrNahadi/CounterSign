# 0034. Claims vs records is one server-side view built in the gate; the console reads the audit log through a read-only gate API opened by the approver key; evidence exports are whole audit-log rows that anyone can re-hash

Status: accepted
Decided-by: autopilot (delegated), phase 10 feature spec, 22 Oct 2026, under brief §14 v1.4. The answerer's rules escalate it, because it sets a service API, an authentication scope and an export file format, all expensive to reverse. The planner session had no way to start the answerer agent, so it applied the answerer's rules itself. Decided by brief §10 trade-offs 1 (fail-closed money safety), 2 (honest evidence) and 4 (a stranger understands it in 60 seconds). The owner can overturn it (`.ralph/human.md`, Decided for you)
Question: Phase 10 shows every decision as "what the message claims" beside "what the records say", on the phone card, in the console and in the agent's trace, and gives the merchant an audit console that lists every intent with its trace and rail response, checks the chain and exports evidence. Where is the two-column view built, how does the console reach the audit log and who may read it, what goes in an evidence export, and how does the agent's trace show the view?
Decision:
- **One builder, in the gate.** `claimsVsRecords` turns a decision entry, its ticket, its seeded order number and its mandate into rows. Each row pairs one thing the message or proposal asserts with the record that checks it, and a verdict worked out by a fixed table from the verifier's result and value: *Matches* or *Contradicts* when the message asserted something the check tests, *Passes* or *Fails* when it didn't, *No record* when the check was unknown, and *Not used* for the message text itself. The phone card, the console's decision page and the `audit` CLI all show the gate's rows; nothing else rebuilds them. No AI, and no attempt to detect lies or injected instructions (brief §5 Out of scope): the message text always gets the same fixed record line, "Messages can't approve money. Only your signed rules can."
- **The records column shows the checks that decided.** The verifiers the matched rules use (`require`, plus any fact a matched rule's `when` tests); when no rule matched, the facts the action's rules test in `when`. The full verifier trace is always shown below it ("How the gate decided"). This settles phase 3's display note (plan.md, "evidence.photo_present fail shows on never-arrived claims").
- **The agent response never carries records.** The agent's trace in Resolve's inbox links each guarded call to its decision page instead. Records hold the payer's email and other merchant-only facts; an agent that saw them could repeat them to whoever wrote in, which is exactly the attacker in beat 3.
- **A read-only audit API on the gate, opened by the approver key.** `GET /audit/decisions`, `/audit/decisions/:seq`, `/audit/intents/:id`, `/audit/entries`, `/audit/verify` and `/audit/export`. It takes the same `COUNTERSIGN_APPROVER_KEY` as the approval API, never a principal key, so no agent can read the log. This amends ADR 0032's "it lets its holder answer step-ups and nothing else": the approver key is the merchant's one credential, and it now also reads the audit log. It still never works on `/mcp`. The console reuses the approvals sign-in cookie and reaches the API from server routes only.
- **Unreadable entries are shown, not hidden.** The approval reader treats one unreadable entry as making everything unknown, because it guards money. The audit console only reads, so an entry it can't parse is listed as unreadable, with its `seq`, type and the parse problem, and its raw payload text on its own page. `ledger verify` stays the tamper check.
- **Evidence exports are whole rows.** An export is one JSON file (`countersign-evidence-v1`) with:
  - its scope (an intent, or a capture with every intent on it and every reconciliation that names one of its refunds);
  - the selected audit-log rows exactly as stored: `seq`, entry type, ref, `at`, the payload's canonical text, `prev_hash` and `hash`;
  - the `mandate.version` rows the decisions point at;
  - the chain verdict and head when it was exported, and the export time.

  `npm run ledger -- check-export <file>` recomputes each row's hash from its envelope and checks that the payload text is canonical. Rows in an export aren't contiguous, so a check proves each row is the one the chain holds, not that no row is missing; the head lets anyone compare with `ledger verify` on the live log. Phase 11's dispute evidence pack builds on this file.
- **The decision list is a Graphite table, not AG Grid.** Brief §15 replaced the original AG Grid audit grid with the AG Studio Risk desk, so phase 10 uses Graphite's Table component (the least visual weight, and nothing to theme).
Basis:
- Brief §5 item 4 ("Every decision shows two columns, 'What the message claims' and 'What the records say', on the phone card, in the console and in the agent's trace. Each fact names its source call and sandbox ID"), item 5 ("see every proposal, decision, verifier trace and rail response in a tamper-evident audit log, check the hash chain, and export it as dispute evidence"), §5 Out of scope ("Classifiers that try to detect lies or injections"), §8 (credential custody; fail closed; every number real), §15 Resolved ("The original AG Grid plan ... is replaced by the AG Studio Risk desk").
- ADR 0018 (reason words with the code beside them; the canvas boards Decisions and Decision detail as the layout reference), ADR 0022 (payloads are canonical text and are parsed for display only, never re-hashed), ADR 0032 (the approver key and its cookie), ADR 0020 (merchant-only details show emails in full; public pages mask them in phase 15).
Consequences:
- Anyone holding the approver key can read every ticket excerpt and payer email in the log. On the hosted demo it's the sandbox-only judge credential (brief §8). Phase 15's public "Attack it yourself" view must mask emails and never use this API's answers as they are.
- The export format is versioned by its `format` field; a change means `countersign-evidence-v2`, never an edit of v1.
- Pairs and verdict words are display only. They never feed a decision, and a test pins that the gate's decision path doesn't import them.
