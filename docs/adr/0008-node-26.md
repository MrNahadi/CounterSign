# 0008. Node 26 locally, in CI and on Render

Status: accepted
Decided-by: answerer (researched)
Question: Phase 1 constitution, Q8. Node version to pin (`engines` and `.node-version`): 26 or 24? Check that Render supports Node 26.
Decision: Put a `.node-version` file containing `26` at the repo root; Render, CI (`actions/setup-node` with `node-version-file`) and fnm all read it. Set `"engines": { "node": ">=26.7.0 <27" }` in the root `package.json`. Spike S7 must confirm that Render installs a 26.x release. If it can't, fall back to 24 by changing those two values; nothing else depends on 26.
Basis:
- Render chooses the Node version from `NODE_VERSION`, then `.node-version`, then `.nvmrc`, then `engines.node`, resolving aliases and semver ranges with node-version-alias. An unbounded range "resolves to the latest Node.js release", so any published 26.x is installable. Render advises always setting an upper bound: https://render.com/docs/node-version. Render doesn't publish a list of supported versions, so this is inferred, which is why S7 checks it.
- The local toolchain, where the Ralph loop runs, is Node 26.7.0. Matching it on Render means a failure shows up locally first, not at deploy time.
- Node 26 enters LTS around 28 Oct 2026, before the first Render deploy in Phase 2, and stays in LTS through judging.
- Dependency engines allow 26: vitest 5 (`^22.12 || ^24 || >=26`), tsx (`>=18`), `@modelcontextprotocol/sdk` (`>=18`), Next.js (`>=20.9`).
Consequences:
- Node 25 and later expose Web Storage globals such as `localStorage` on the server. Server code must not sniff `localStorage` to detect a browser; use `typeof window !== "undefined"`. Load AG Studio client-only.
