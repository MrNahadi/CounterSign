# 0028. The gate's MCP surface: one low-level `Server` per request, principal keys as bearer tokens, every guarded call recorded, `ACTION_UNAVAILABLE` for allows the gate can't execute, and pass-through reads served by the rail client

Status: accepted, amends ADR 0001 (`registerTool` becomes the low-level `Server`'s `tools/list` and `tools/call` handlers; everything else in ADR 0001 holds)
Decided-by: autopilot (delegated), phase 7 feature spec, 18 Oct 2026, under brief §14 v1.4. The answerer's rules escalate it, because it is the gate's public API and amends an accepted ADR. The planner session couldn't reach the answerer agent, so it applied the answerer's rules itself. Decided by brief §10 trade-offs 1 (fail closed, credential custody), 2 (honest evidence: every proposal in the log) and 5 (PayPal depth). The owner can overturn it (`.ralph/human.md`, Decided for you)
Question: Phase 7 puts the gate behind MCP. How does an agent authenticate as a principal? How are tools declared and validated, given that an invalid proposal must be denied and logged, not refused as a protocol error? What does a guarded tool return? What happens when the mandate allows an action the gate has no executor for yet? How do read-only tools reach PayPal, and which ones exist?
Decision:
- **Transport (ADR 0001, unchanged):** `POST /mcp`, stateless Streamable HTTP in JSON mode, a new server and transport per request; `GET` and `DELETE /mcp` answer 405.
- **Principal keys.** An agent sends `Authorization: Bearer <key>`. Keys come from environment variables, one per principal: `COUNTERSIGN_SUPPORT_AGENT_KEY` in this phase (`COUNTERSIGN_OPS_AGENT_KEY` joins in phase 12). A key under 32 characters counts as unset. The gate compares SHA-256 digests with a constant-time comparison. A missing, malformed or unknown key gets HTTP 401 with a fixed body and no hint of which principals exist; the MCP server is never built for it. The key picks the principal, and the principal picks its mandate: `support-agent` uses the demo mandate `kikapu-studio` v3 (`packages/mandate/fixtures/kikapu-studio-v3.json`) until phase 17 stores signed versions. Nothing in a request can name a different principal.
- **Low-level `Server`, not `registerTool`.** The gate builds `Server` from `@modelcontextprotocol/sdk/server/index.js` with its own `tools/list` and `tools/call` handlers. `tools/list` advertises each tool's input JSON Schema, generated from the same zod schema the gate normalizes with (`z.toJSONSchema`). `tools/call` hands the raw arguments to the gate without validating them first, so a malformed guarded call is denied `INVALID_PROPOSAL` and recorded in the audit log like any other proposal. `registerTool` would validate first and answer a protocol error that never reaches the log.
- **Guarded tool calls.** The tool's arguments are PayPal's (per ADR 0027), plus a `justification` object (`ticket_id`, `claim`). The result is the agent response (original brief §6) as `structuredContent` and as JSON text, with `isError: false` for every decision, deny included: a denial is an answer, not a failure. An unknown tool name is `UNKNOWN_ACTION`, recorded. Only a recording failure (nothing written, nothing executed) answers `isError: true`, with a fixed message.
- **What executes.** Refunds execute as in phase 6. For any other action, an `allow` from the mandate is turned into a `deny` by the gate's `decide()`, with a new code, `ACTION_UNAVAILABLE` ("Countersign can't carry out this action yet."), keeping the intent, trace and matched rules, so the agent is never told `allowed` for something that won't happen. Step-ups are recorded and wait, as in phase 6. Phase 9 adds invoice send, phase 11 the dispute calls and phase 12 payouts.
- **Read-only tools** keep PayPal's names and argument shapes and are answered by `@countersign/rail-paypal` and the carrier mock, never by spawning the Agent Toolkit: `get_order`, `get_refund`, `list_disputes`, `get_dispute`, `get_shipment_tracking` (the order's trackers, each with the simulated carrier's status) and `list_transactions` (Transaction Search). They return the rail client's parsed records with money as PayPal's `{ value, currency_code }`, labelled where simulated. They need a principal key but aren't written to the audit log. A read that fails answers `isError: true` with the read problem's fixed line. `get_mpesa_receipt` joins in phase 18.
- **New rail calls:** `GET /v1/customer/disputes/{id}`, `GET /v2/invoicing/invoices/{id}` and `GET /v1/reporting/transactions`, each parsed with zod into minor units, sandbox only.
Basis:
- Brief §5 item 1 ("keeps PayPal's tool names where the Agent Toolkit has them and adds Countersign extensions where it doesn't. Read-only tools pass straight through"), §8 ("The agent never holds PayPal or Daraja credentials", fail closed), §3 ("switching is one URL change").
- Original brief §12 security controls: "Each agent authenticates with a key scoped to its principal and mandate."
- tech-stack.md: "Only `@countersign/rail-paypal` calls PayPal REST or knows its JSON"; ADR 0011: "If the gate uses the toolkit for read pass-through, it uses the same out-of-process MCP client pattern and never imports the toolkit." Serving reads from the rail client keeps one PayPal client, its sandbox-only base URL guard and its contract tests, and needs no child process on Render.
- MCP SDK 1.32.1: `McpServer.registerTool` parses arguments against `inputSchema` before the handler runs; the low-level `Server` with `setRequestHandler(CallToolRequestSchema, …)` does not. Tool results carry `content`, optional `structuredContent` and `isError` (MCP spec 2025-11-25, Tools).
Consequences:
- The human creates `COUNTERSIGN_SUPPORT_AGENT_KEY` (32+ random characters) in the Dev environment, `.env.example` and later Render (`.ralph/human.md`).
- Resolve (phase 8) uses the same key in protected mode.
- Rate limits per session come with "Attack it yourself" (phase 15); this phase adds none.
- Arguments the toolkit accepts but the gate doesn't send (a refund's `invoice_id` and `note_to_payer`) are accepted and ignored, so an agent written for PayPal's server isn't refused for them.
