# 0003. Postgres through Drizzle 0.45 (postgres.js on Render, PGlite in tests); audit-log appends serialized by an advisory lock

Status: accepted
Decided-by: answerer (researched)
Question: Phase 1 constitution, Q3. Postgres access layer: Drizzle ORM 0.45 + postgres.js with PGlite in Vitest, or something else? How do we serialize hash-chained audit-log appends? Do drizzle-kit migrations run on both PGlite and Render Postgres?
Decision:
- Pin `drizzle-orm` 0.45.4 and `drizzle-kit` 0.31.11, not the 1.0 RC. Use `postgres` 3.4.9 against Render Postgres 18, and `@electric-sql/pglite` 0.5.10 (in memory) in Vitest.
- Keep one schema and one migrations folder, generated by `drizzle-kit generate`. Apply them with `migrate()` from `drizzle-orm/postgres-js/migrator` (as a Render pre-deploy command) and from `drizzle-orm/pglite/migrator` (in test setup).
- Append to the audit log in a single READ COMMITTED transaction:
  1. `SELECT pg_advisory_xact_lock(<fixed bigint key>)`.
  2. Read the tail with `ORDER BY seq DESC LIMIT 1`.
  3. Compute `hash` over `prev_hash` plus the canonical serialization of the entry.
  4. Insert with `seq = tail.seq + 1`.
- Backstops: `seq` is the primary key, and `prev_hash` is UNIQUE, so a forked chain can't be inserted.
- Don't lock the tail row with `SELECT ... FOR UPDATE`. Don't run appends at REPEATABLE READ or SERIALIZABLE.
Basis:
- Brief §7: "Audit log: Append-only, hash-chained record ...". Brief §9, Storage: "Postgres on Render".
- `drizzle-orm` 0.45.4 has the peer dependencies `"@electric-sql/pglite": ">=0.2.0"` and `"postgres": ">=3"`, and it exports `./pglite/migrator` and `./postgres-js/migrator` (npm registry). PGlite driver: https://orm.drizzle.team/docs/connect-pglite. The npm dist-tags are `latest` 0.45.4 and `rc` 1.0.0-rc.4.
- PGlite 0.5.0 upgraded to Postgres 18.3 (pglite CHANGELOG). Render supports Postgres 18 for new databases: https://render.com/docs/postgresql-upgrading
- Transaction-level advisory locks "are automatically released at the end of the transaction": https://www.postgresql.org/docs/current/explicit-locking.html
- In READ COMMITTED, each statement takes a new snapshot. `SELECT FOR UPDATE` "will only find target rows that were committed as of the command start time", so two appenders that lock the old tail would both chain from it. REPEATABLE READ fixes its snapshot at the first statement, which comes before the lock wait: https://www.postgresql.org/docs/current/transaction-iso.html
Consequences:
- Tests need no Docker: each test file creates an in-memory PGlite and runs the migrations.
- PGlite has one connection, so tests can't produce real lock contention. Tests prove the UNIQUE(`prev_hash`) backstop instead: inserting a forked row must fail. They also prove that `ledger verify` catches an edited row.
- Hash a canonical serialization computed in the app (for example RFC 8785 JCS) and store exactly what was hashed. Never re-hash jsonb text read back from Postgres, because jsonb reorders keys and normalizes whitespace. Store money in integer minor units, and store timestamps as the ISO string that was hashed.
- The Drizzle docs site now defaults to the 1.0 RC (`drizzle-orm@rc`). Write code against the 0.45 API, such as `drizzle({ client })` and `migrate(db, { migrationsFolder })`.
- Schema, migrations and the client factories (postgres.js for runtime, PGlite for tests) live in one workspace package, suggested name `packages/db`. That's a refinement of original §12's layout.
- Create the Render database on Postgres 18 to match PGlite.
