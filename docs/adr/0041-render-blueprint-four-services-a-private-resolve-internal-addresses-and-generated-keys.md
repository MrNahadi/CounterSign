# 0041. Countersign runs on Render from one blueprint: four paid services with Resolve private, one internal-only Postgres 18, a reconcile cron, internal addresses from `hostport`, and keys Render generates

Status: accepted, applies ADRs 0001, 0007, 0008, 0009, 0028, 0030 and 0032 to hosting (nothing in them changes)
Decided-by: autopilot (delegated), phase 13 design draft, 25 Oct 2026, under brief §14 v1.4. It's a critical decision (`.ralph/egm/PROCESS.md`): it fixes the Render contract and decides where every secret lives. The planner session had no way to start the answerer agent or a Goldfish sub-agent, so it applied the answerer's rules itself and wrote the strongest case against its own choice below; round A's Design Critic reviews it fresh. Render's blueprint fields are researched. Decided by brief §10 trade-offs 1 (fail closed, credential custody) and 3 (the judge path works every time). The owner can overturn it (`.ralph/human.md`, Decided for you)
Question: Phase 13 puts the demo on Render (brief §5 items 8 and 18, spike S7). Which services exist and of what type, how do they find each other, where does each secret live and who creates it, how is the database reached, and how is the blueprint checked when no agent can deploy it?
Decision:
- **One `render.yaml` at the repo root**, the only deploy config. It declares, all in `oregon` and all on the smallest paid plans (`0.5c-512mb` for services and the cron job, `0.1c-256mb` for Postgres; brief §9 rules out free plans):
  - `countersign-gate` (web, public): `/mcp`, the approval, audit and demo-reset APIs, and `/webhooks/paypal`. Health check `/health`. Its pre-deploy command is `npm run db:migrate`.
  - `countersign-console` (web, public): the console. Health check `/`.
  - `countersign-storefront` (web, public): the Kikapu shop. Health check `/`.
  - `countersign-resolve-agent` (private service, `pserv`): never reachable from the internet; only the console's server routes, the gate's dispute nudge and the cron job call it (ADR 0030). `PORT` is set to `10000`.
  - `countersign-reconcile` (cron, every 10 minutes): `npm run reconcile`, then `npm run disputes -- sync`, a safety net for missed webhooks.
  - `countersign-db` (Postgres 18) with `ipAllowList: []`, so only Render's private network reaches it. Checks on the hosted database run from the gate's Render Shell.
- **Build and start.** Every service builds from the repo root with `npm ci --include=dev` (the Next apps then run `npm run build --workspace <app>`) and runs from source with tsx (ADR 0007). `NODE_VERSION` is `26.7.0` on every service, so Render can't pick another Node (ADR 0008, spike S7). The Next apps start with `-H 0.0.0.0`; Render sets `PORT`.
- **Internal addresses come from Render's `hostport` property**, never a guessed hostname. Each caller gets `<SERVICE>_HOSTPORT` through `fromService … property: hostport`, and its start command turns it into the URL variable the code already reads: `GATE_MCP_URL=http://$GATE_HOSTPORT/mcp` (Resolve), `GATE_URL=http://$GATE_HOSTPORT` and `RESOLVE_AGENT_URL=http://$RESOLVE_AGENT_HOSTPORT` (console), `RESOLVE_AGENT_URL=http://$RESOLVE_AGENT_HOSTPORT` (gate and cron). Traffic between services stays on the private network over plain HTTP. No code changes for addresses.
- **Secrets.** Nothing secret is in the file.
  - Render generates the three Countersign keys on the gate (`generateValue: true`): `COUNTERSIGN_SUPPORT_AGENT_KEY`, `COUNTERSIGN_OPS_AGENT_KEY` and `COUNTERSIGN_APPROVER_KEY` (44 base64 characters each, above the 32-character minimum). Resolve reads the support key from the gate with `fromService … envVarKey`, so the two always match. The approver key is the judges' approver login; the owner copies it from the dashboard into the Devpost testing instructions, never into the repo.
  - Every other secret is `sync: false`, typed into the dashboard once: `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET` (gate, Resolve, storefront, cron), `PAYPAL_WEBHOOK_ID` (gate), the two seed vault tokens (gate, for the demo reset, ADR 0042) and `GEMINI_API_KEY` (Resolve only).
  - The console gets no `GEMINI_API_KEY` until phase 16, so the Risk desk spike route can't spend on the public URL.
  - `PAYPAL_BASE_URL` is the sandbox URL, written in the file, because the rail client refuses any other (brief §8).
- **Fixed settings in the file:** `COUNTERSIGN_DEMO_RESET=on` (gate, ADR 0042), `RESOLVE_BASELINE=scenarios` (Resolve, ADR 0043) and `RESOLVE_DAILY_RUN_CAP=200` (Resolve, ADR 0031). `STOREFRONT_URL` (console, optional) is `sync: false`, because a service can't read another service's public URL from the blueprint.
- **One instance of each service.** The gate's demo reset and in-flight execution count are in-process (ADR 0042), so the gate must stay at one instance.
- **Checked without deploying.** A repo-level Vitest test parses `render.yaml` (with `yaml` 2.9.1, a new root devDependency) and pins the services, types, plans, commands, health checks, every `fromService` and `fromDatabase` reference, and each service's variables, and refuses any value that looks like a secret. Deploying it is the owner's (`.ralph/human.md`).
Basis:
- Brief §5 item 18 ("paid Render plans, automatic token refresh, an uptime monitor, a daily smoke test"), §8 (the hosted demo stays up to 22 Dec; no secrets in the repo; judge credentials are sandbox-only; the agent never holds PayPal credentials; the public demo can't run up unbounded AI cost), §9 Hosting ("Render paid web services (free ones spin down), Postgres, and a cron job for reconciliation"), §10 trade-offs 1 and 3, §15 decision 7 (paid plans until 22 Dec), §12 (judge guide: "approver login").
- Render Blueprint spec (read 25 Oct 2026): `type: pserv`, `preDeployCommand`, `healthCheckPath`, `sync: false`, `generateValue`, `fromDatabase … connectionString`, `fromService … property: hostport` ("Use this value to connect to the service over the private network. Example: `my-service:10000`") and `envVarKey`, `ipAllowList: []` ("Only allow internal connections"), `postgresMajorVersion`, the compute plan IDs, and that `sync: false` can't be used inside an environment group: https://render.com/docs/blueprint-spec
- Render's own blueprint examples expand variables in start commands (`--port $PORT`) and pass a `hostport` to another service: https://render.com/articles/deploying-multi-agent-systems-without-aws-complexity
- ADR 0030 (the console reaches Resolve only from server routes), ADR 0031 (`RESOLVE_DAILY_RUN_CAP`), ADR 0032 (the approver key is read by the gate only), `docs/spikes.md` S4 (keep baseline off the public path) and S7 (not started).
Goldfish argument (the Elephant's own steelman, since no fresh sub-agent could be started): "Start-command prefixes hide configuration in shell strings that nothing type-checks; a typo in `$GATE_HOSTPORT` fails only at runtime. Generated keys mean the owner must copy 44-character base64 strings by hand into the agent CLI and Devpost, and a generated approver key published to judges is effectively public. An internal-only database means every live check needs the Render Shell. Code that accepts a `hostport` directly, keys the owner chooses, and a database open to credentials would be simpler to operate."
Answer: The blueprint test pins every prefix against the variable names the code reads, so a typo fails `npm test`, not a deploy; a code-side fallback would add a second way to set every address. The approver key is meant for judges (brief §12, "approver login"), sandbox-only (§8), and lives in the Devpost testing instructions rather than the repo; generating it means no weak or reused key ever exists. An internal-only database is the fail-closed choice (§10 trade-off 1, absolute), and the Render Shell is available on paid plans. The arguments are close only on operating effort, so the fail-closed options stand.
Consequences:
- The owner creates the blueprint, enters the `sync: false` values, and, after the first deploy, copies the generated keys where they're needed, registers the PayPal webhook at `<gate URL>/webhooks/paypal` and presses Reset once to seed (`docs/hosting.md`).
- Spike S7's checks (Node 26 installed, webhooks reaching the gate over HTTPS) are the owner's live checks in phase 13's `validation.md`.
- Phase 19 adds the smoke-test cron and the uptime monitor to the same file.
- Raising any service above one instance needs the reset and in-flight count moved to the database first.
