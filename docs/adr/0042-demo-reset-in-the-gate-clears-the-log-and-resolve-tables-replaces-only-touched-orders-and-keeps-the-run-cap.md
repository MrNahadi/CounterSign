# 0042. The demo reset runs in the gate behind the approver key and a demo flag; it clears the audit log and Resolve's tables under the ledger lock, records where the old log ended, replaces only the seeded orders whose captures changed, records open disputes again, and never resets the day's run cap

Status: accepted, refines ADR 0023's consequence for phase 13 ("start a fresh seed run, or reuse the current one when its captures are still unrefunded") to a per-order rule; extends ADRs 0022 (a new entry type) and 0035 (dispute sync as a function)
Decided-by: autopilot (delegated), phase 13 design draft, 25 Oct 2026, under brief §14 v1.4. It's a critical decision (`.ralph/egm/PROCESS.md`): it changes what can move money (it creates sandbox orders), touches the tamper-evident audit log and changes what a judge sees. The planner session had no way to start the answerer agent or a Goldfish sub-agent, so it applied the answerer's rules itself and wrote the strongest case against its own choice below; round A's Design Critic reviews it fresh. Decided by brief §10 trade-offs 1 (fail closed), 2 (honest evidence) and 3 (the judge path works every time). The owner can overturn it (`.ralph/human.md`, Decided for you)
Question: Brief §5 item 8 and §11 need a reset that restores the seed state in 60 seconds or less. Which service runs it, who may run it, what does it clear, how does it avoid clearing work in flight, how does it restore orders that a scenario refunded, what happens to open disputes, and what stops a reset from resetting the AI spend guard?
Decision:
- **The gate runs it**, because it already writes the audit log, holds the PayPal credentials and owns dispute sync. The seed catalog and seed run move from the storefront into a new package, `@countersign/seed` (with the product list they use), so the gate and the storefront's `npm run seed` share one implementation. The gate also needs the two seed vault tokens.
- **Off unless the database is a demo.** The gate mounts `POST /demo/reset` and the `npm run reset` CLI runs only when `COUNTERSIGN_DEMO_RESET` is exactly `on`. Otherwise the route doesn't exist (404) and the CLI refuses (exit 2). The route takes only the approver key (ADR 0032), checked before anything else; principal keys never work there.
- **Checks before anything changes.** A database, PayPal's variables and both vault tokens must be present (503, naming variables, never values). Only one reset runs at a time (409). The reset refuses while the gate is carrying out an execution (an in-process count around `execute()`, 409).
- **One transaction clears everything, under the ledger's advisory lock** (ADR 0003), with `lock_timeout` 5 seconds:
  1. Lock `audit_log`, `tickets`, `ticket_attachments`, `agent_runs`, `dispute_drafts` and `evidence_documents` in `ACCESS EXCLUSIVE` mode. A lock not granted in 5 seconds ends the reset with 409 and nothing changed.
  2. If any agent run or dispute draft is `queued` or `running`, stop with 409 ("Resolve is still working"), nothing changed. Resolve's own writes wait on the locks, so none can slip in.
  3. Read the log's head and row counts, add each UTC date's run and draft counts to a new table, `cleared_run_counts`, and `TRUNCATE` the six tables. Row triggers don't fire on TRUNCATE, which ADRs 0022 and 0035 left open for exactly this.
  4. Append a new entry type, **`demo.reset`**, as entry 1 of the new log: `{ previous_head: { seq, hash } | null, cleared: { entries, tickets, attachments, runs, drafts, documents } }`, ref null. It says the log restarted and where the old one ended; it proves nothing about the old rows, and the console says so.
  `seed_orders` and `carrier_shipments` aren't cleared: seed rows are replaced per order below, and every shipment's tracking number names its run, so old shipments never collide and a dispute on an older capture still finds its carrier record.
- **Replace only what changed.** After the commit, the gate reads every seeded order's capture (`GET /v2/payments/captures/{id}`, 3 at a time). An order is kept when its row reads, belongs to the catalog's buyer, and its capture is `COMPLETED`. Any other status, a read that fails, or a missing row means it's replaced: one new seed run (a new run ID) creates just those orders, and its rows replace theirs. On an empty database every order is replaced, so the first reset is the hosted seed. A typical judge session touches a few captures, so a reset replaces a few orders, well inside 60 seconds.
- **Open disputes come back.** The gate then runs the same sync as `npm run disputes -- sync` (now a shared function), which records every dispute waiting for the seller as `dispute.received` again and nudges Resolve to draft its evidence.
- **The run cap survives.** Resolve's daily cap counts today's runs and drafts plus today's `cleared_run_counts`, so resetting never buys more AI calls (brief §8).
- **Partial is reported, not hidden.** Once the transaction has committed, a seed order or dispute that fails is listed in the answer (`complete: false`), and resetting again retries it. A failure before the commit changes nothing.
- **The answer** (`200`) gives the time taken, the counts cleared, the old head, the orders kept and replaced (with the new run ID), any seed failures, and the disputes recorded. The console turns it into one sentence.
Basis:
- Brief §5 item 8 ("reset the demo to the seed state"), §11 ("Demo reset takes ≤ 60 seconds"), §12 ("Reset restores the seed state in ≤ 60 seconds"; "Re-sending the same intent creates no second refund in the sandbox"; "`ledger verify` passes on the hosted database"), §8 (sandbox only; AI spend has a daily cap; fail closed), §10 trade-offs 1 to 3.
- Original brief §12 ("Data: sandbox data only, purged on demo reset"), §15 ("Rehearse with the demo reset button").
- ADR 0023 (seed runs are named and resumable; "Phase 13's reset can start a fresh seed run, or reuse the current one when its captures are still unrefunded, and truncate these tables with the audit log"), ADR 0022 and migration 0000 (TRUNCATE stays possible for the demo reset), ADR 0035 and migration 0005 (the same for evidence documents), ADR 0030 (runs are rows; interrupted runs are never rerun), ADR 0031 (`RESOLVE_DAILY_RUN_CAP`), ADR 0037 (failed drafts count against the cap).
- PayPal capture status values (`COMPLETED`, `PARTIALLY_REFUNDED`, `REFUNDED`, `DECLINED`, `PENDING`, `FAILED`): https://developer.paypal.com/docs/api/payments/v2/#captures_get
Goldfish argument (the Elephant's own steelman, since no fresh sub-agent could be started): "A route on the public gate that truncates the tamper-evident log, guarded by a key that's handed to every judge, is exactly the kind of power the project says agents shouldn't have. Anyone with the key can wipe evidence or thrash the demo during another judge's session. Putting it in the private Resolve service, or making it a CLI only the owner runs, would keep the wipe off the internet. The per-order reseed also leaves `seed_orders` mixing run IDs, which is harder to reason about than one fresh run."
Answer: The reset is the brief's own requirement for judges (§5 item 8: "a judge can … reset the demo"), so an owner-only CLI cuts scope, which the brief forbids. Resolve can't host it without importing the gate's dispute code and the ledger's writes, and its private network position wouldn't change who can trigger it: the console route would still accept the same key. What keeps it honest is that it's off unless the flag says the database is a demo, it records the old head in a `demo.reset` entry rather than wiping silently, `ledger verify` passes on the new chain, money only moves into the sandbox merchant's account from sandbox buyers, and it can't run while Resolve or an execution is mid-flight. Mixed run IDs are already how ADR 0023 keys rows (run ID per row, tracking number per run), and the per-order rule is what keeps a typical reset well under 60 seconds (§10 trade-off 3). Thrashing by a key holder is a phase 15 rate-limit concern; one reset at a time bounds it now.
Consequences:
- `@countersign/seed` is a new workspace; the storefront's seed CLI and its tests import from it, and the no-AI test covers it.
- `@countersign/db` gains migration 0007 (`cleared_run_counts`) and the reset's table helpers; `@countersign/ledger` gains the `demo.reset` entry type; the gate's audit reader gives it a summary line.
- The gate must run as one instance (ADR 0041).
- A dispute opened on an order that a scenario refunds is left on a replaced order; the owner opens beat 7's dispute on `KIK-1032`, whose role is `dispute` and which no scenario touches (`.ralph/human.md`).
- The reset can't prove what the old log held; an evidence export taken before a reset still verifies on its own (ADR 0034).
