# 0035. Disputes arrive as `dispute.received` entries; the gate builds a write-once evidence PDF whose hash is inside the intent; Resolve's drafter writes only the notes; the three dispute actions execute at most once

Status: accepted, extends ADRs 0027 (dispute targets and hashed parameters) and 0033 (one executor per action)
Decided-by: autopilot (delegated), phase 11 feature spec, 22 Oct 2026, under brief §14 v1.4. The answerer's rules escalate it, because it adds an audit-log entry type, a stored document format, a new MCP extension and a service-to-service call, all expensive to reverse. The planner session had no way to start the answerer agent, so it applied the answerer's rules itself; the PayPal call shapes are researched. Decided by brief §10 trade-offs 1 (fail-closed money safety), 2 (honest evidence), 3 (the judge path works every time) and 5 (PayPal depth). The owner can overturn it (`.ralph/human.md`, Decided for you)
Question: Phase 11 turns a dispute webhook into an evidence pack that the merchant approves and that's submitted with `provide-evidence`. How does a dispute reach the audit log without a public URL, what is the evidence pack and how is it bound to the approval, who drafts it and with what, and how do the dispute actions execute?
Decision:
- **Intake.** A verified `CUSTOMER.DISPUTE.CREATED` webhook (the same signature check as ADR 0025) makes the gate re-read the dispute with get dispute, never trusting the event body, and append a new entry type, `dispute.received` (`refId` = the dispute ID): source `webhook` or `poll`, the event's ID and type (null when polled), and the dispute as re-read (status, reason, life-cycle stage, amount, seller response due date, disputed capture IDs). One entry per webhook event ID, and at most one per dispute from polling. Until phase 13's public URL, `npm run disputes -- sync` polls the merchant's disputes that wait for the seller and logs any dispute with no `dispute.received` entry yet. `CUSTOMER.DISPUTE.UPDATED` and `.RESOLVED` are acknowledged and ignored.
- **The nudge.** After a `dispute.received` entry is written, the gate tells Resolve with `POST <RESOLVE_AGENT_URL>/disputes { dispute_id }`, best effort, with a 2 second timeout, after the webhook's answer is decided and never changing it. Resolve also takes the same call from the console and its CLI, so a missed nudge is one click to repeat. Drafting is idempotent per dispute.
- **Evidence documents, write-once, hashed.** The gate builds the pack's facts deterministically (no AI) from records: the dispute, the disputed capture and its order, the order's trackers, the carrier mock's status and scans (labelled simulated), the capture's refunds, Countersign's decisions on that capture (time, action, decision, reason codes; never a payer email or message text) and phase 10's capture-scoped evidence export. It stores two documents in a new write-once `evidence_documents` table: the export JSON, and a PDF (built with `pdf-lib`) that prints the facts, the chain verdict and head, and the export's SHA-256. PayPal accepts only image and PDF files, so only the PDF is sent; the JSON lets anyone check the PDF's claims with `ledger check-export`.
- **A new non-guarded extension, `prepare_dispute_evidence { dispute_id }`.** It builds and stores the documents and answers the facts (as above, masked), the document IDs, names, sizes and SHA-256s, and suggested evidence items whose type, tracking numbers and refund IDs come from a fixed table over the facts. It moves no money, so it isn't decided, but it is only offered to principal keys, like every MCP tool.
- **The intent binds the pack.** `provide_dispute_evidence` gains `document_ids` (1 to 5) and each evidence item gains optional `refund_ids`. The gate reads each document from the store; a document that's missing, isn't a PDF, or belongs to another dispute makes the proposal `INVALID_PROPOSAL`. The hashed parameters become the evidence list plus `documents: [{ id, name, sha256 }]`, so an approval binds the exact file bytes. The executor reads the bytes by ID and refuses to send if their SHA-256 differs (recorded `failed`, nothing sent).
- **The drafter lives in Resolve, writes only notes.** A dispute draft is one run in Resolve: it calls `prepare_dispute_evidence` over MCP with the support agent's principal key, then makes one Gemini structured-output call that writes a summary and one note per suggested item from the facts alone, then proposes `provide_dispute_evidence` with the suggested types, tracking numbers, refund IDs and documents set by code, and the model's notes. The run never has a loop, tools or a free choice of evidence type. If the model is unavailable, blocked, over the daily run cap or answers outside the schema, the notes come from a fixed template over the same facts, and the draft records `drafted_by: template`, so the judge path never depends on Gemini. The mandate steps every dispute action up, so nothing is submitted without the merchant.
- **Executors for all three dispute actions**, used by both paths (allow and approval): accept claim (`POST …/accept-claim` with the note), make offer (`POST …/make-offer` with type, amount, note) and provide evidence (`POST …/provide-evidence` as `multipart/form-data`: an `input` part holding the `evidences` JSON and one file part per document). PayPal's dispute calls document no `PayPal-Request-Id`, so, as for invoice sends (ADR 0033), each is sent once, with none, and never retried or re-sent. A 2xx is `executed`; a 4xx `failed`; anything else `unknown`, counting as sent. The result holds `dispute: { id, status }`, the status re-read with get dispute after the call (null if that read fails). Executed dispute actions count in today's usage, the conservative side.
- **Sandbox helpers.** `npm run disputes -- require-evidence <id>` and `adjudicate <id> --favor seller|buyer` call PayPal's sandbox-only endpoints to move a test dispute along (spike S3). They're operator commands, never MCP tools, and the rail client already refuses any base URL but the sandbox's.
Basis:
- Brief §5 item 13 ("When the dispute webhook arrives, the agent drafts evidence from the audit log and tracking, the owner approves it, and it's submitted with `provide-evidence`"), §6 beat 7, §8 (no AI in the decision path; fail closed; what you approve is what executes; every number real, simulation labelled), §13 spike S3, cut line ("If spike S3 fails, item 13 becomes the evidence pack plus a recorded sandbox submission").
- Original brief §9 (`paypal.dispute.provide_evidence` "Always step-up (the merchant reviews the evidence pack)"), §13 ("Evidence drafting … Builds the dispute evidence narrative from audit-log facts and tracking … Always step-up").
- PayPal Customer Disputes v1 (read 22 Oct 2026): provide-evidence, accept-claim and make-offer paths; the sandbox-only `require-evidence` (`action`: `BUYER_EVIDENCE` | `SELLER_EVIDENCE`, needs `UNDER_REVIEW`) and `adjudicate` (`adjudication_outcome`: `BUYER_FAVOR` | `SELLER_FAVOR`); `make_offer` requires `note` and `offer_type`; evidence `notes` 1 to 2000 characters, `evidence_info.tracking_info` and `refund_ids`; document names `^[A-Za-z0-9-_,\s]+[.]{1}[A-Za-z]+$`: https://developer.paypal.com/api/customer-disputes/v1/schema.yaml and https://developer.paypal.com/docs/api/customer-disputes/v1/
- PayPal "Use the Disputes API" (the provide-evidence curl: `-F 'input={"evidences":[…]};type=application/json' -F 'file1=@NewDoc.pdf;type=application/pdf'`; accept-claim body `{ "note": … }`): https://developer.paypal.com/platforms/disputes/handle-disputes/use-disputes-api
- PayPal "Test and go live" for disputes (create a sandbox dispute as the buyer; require-evidence and adjudicate need `UNDER_REVIEW`): https://developer.paypal.com/platforms/disputes/test-go-live
- ADRs 0025, 0027, 0028, 0033, 0034.
Consequences:
- `@countersign/ledger` gains the `dispute.received` entry type; the audit reader and console summarise it.
- A new table, `evidence_documents`, and in Resolve a `dispute_drafts` table; one migration each.
- The gate gains `RESOLVE_AGENT_URL` (default `http://127.0.0.1:8788`), the same variable the console reads.
- Accepted file types and size limits for evidence documents aren't in the schema text read; the PDF is kept under 1 MB and the live check confirms PayPal accepts it.
- Creating a sandbox dispute needs a sandbox buyer login, so it's the owner's step (`.ralph/human.md`). Everything else is proven against fixtures, with the live submission under `LIVE=1` once a dispute ID is set.
