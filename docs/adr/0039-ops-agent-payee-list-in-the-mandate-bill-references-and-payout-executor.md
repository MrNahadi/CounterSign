# 0039. The ops agent has its own key and mandate; the payee list lives in the signed mandate; a payout names its bill reference; payouts execute once with the intent hash as request ID and the intent ID as batch ID, and reconcile by poll and webhook

Status: accepted, extends ADRs 0027 (the payout target and hashed parameters), 0028 (principal keys), 0033 (one executor per action) and 0026 (execution entries)
Decided-by: autopilot (delegated), phase 12 feature spec, 23 Oct 2026, under brief §14 v1.4. The answerer's rules escalate it, because it changes the mandate schema (which phase 17's compiler targets), a stored intent format, an audit-log payload and adds a principal, all expensive to reverse. The planner session had no way to start the answerer agent, so it applied the answerer's rules itself; the PayPal call shapes are researched. Decided by brief §10 trade-offs 1 (fail-closed money safety), 2 (honest evidence), 4 (a stranger understands it) and 5 (PayPal depth). The owner can overturn it (`.ralph/human.md`, Decided for you)
Question: Phase 12 lets an ops agent pay an allowlisted supplier through PayPal Payouts, always with step-up, while the support agent's payouts are denied. How does the ops agent authenticate, where does the supplier list live and how is it checked, what stops the same supplier bill being paid twice, how does a payout execute and reconcile, and is the ops agent an AI?
Decision:
- **A second principal, `ops-agent`.** Its key is `COUNTERSIGN_OPS_AGENT_KEY` (32+ characters, as ADR 0028), and its mandate is a new fixture, `packages/mandate/fixtures/kikapu-studio-ops-v1.json` (`id: kikapu-studio-ops`, version 1, principal `ops-agent`, fallback deny). Two principal keys with the same value both count as unset, and the approver key must differ from every principal key (ADR 0032). The support agent's mandate, file and hash are unchanged: it has no payout rule, so its payouts stay denied `NO_MATCHING_RULE` (original brief §7 rule 6).
- **The payee list is part of the signed mandate.** The mandate schema gains an optional `payees` list: `{ email, name }`, at most 100, emails written lower-cased and trimmed, no repeats. A mandate without the key hashes exactly as before. The ops mandate's one rule, `payout-listed-supplier`, matches every `paypal.payout`, requires `payee.allowlisted` and decides `step_up` with `ALWAYS_NEEDS_APPROVAL`. The demo list names two illustrative suppliers at `example.com` addresses.
- **`payee.allowlisted` is a pure verifier.** The gate's `decide()` passes the deciding mandate's list to the verifiers as a record snapshot (`payees`, call `mandate payees`, ID `<mandate id> v<version>`), always replacing anything the proposal's records hold. The verifier passes when the payout's normalized email is on the list (naming the payee), fails when it isn't, and is unknown when there's no list or the intent isn't a payout. New reason codes: `PAYEE_NOT_ALLOWLISTED` (fail) and `PAYEE_LIST_UNKNOWN` (unknown), each with words and a reply hint.
- **A payout names the bill it pays.** `create_payout` (a Countersign extension) gains a required `reference`, the supplier's bill or invoice number (1 to 63 characters of letters, digits and `._/-`, since PayPal's `sender_item_id` holds 63). It's a hashed parameter, hashed only when set (as ADR 0035's documents), so every intent hash in existing tests is unchanged and a proposal without one is `INVALID_PROPOSAL`. The same bill, payee, amount and note is one intent, so it's paid at most once; a new bill is a new intent. Payouts are USD only (PayPal Payouts doesn't pay KES); another currency is `INVALID_PROPOSAL`. Payouts have no ticket (ADR 0027).
- **The payout executor.** `POST /v1/payments/payouts` with `PayPal-Request-Id` = the intent hash, `sender_batch_header.sender_batch_id` = the intent ID, `recipient_type: EMAIL`, a fixed `email_subject` ("You have a payment from Kikapu Studio (illustrative)"), and one item: the amount, the receiver, the note when set and `sender_item_id` = the reference. The gate sends it once, like an invoice send: a re-proposed or re-approved intent is never sent again. The rail client may retry its own POST after a 5xx or network error, because the request ID and batch ID make that safe (PayPal: "If you receive an HTTP 5nn status code, you can safely retry the request with the same `sender_batch_id`"). After a 201, the batch is read once to find the item. Outcomes: a batch `PENDING`, `PROCESSING`, `SUCCESS` or `NEW` is `executed`; `DENIED` or `CANCELED` is `failed`; a 4xx is `failed`, except PayPal's refusal of a reused `sender_batch_id`, which is `unknown` (an earlier send may have paid); anything else is `unknown`. The result holds `payout: { batchId, batchStatus, item: { id, status } | null }` (item null when the read fails). Executed payouts count in the ops agent's usage.
- **Reconciliation.** A payout item's status changes after the call (`UNCLAIMED` until the payee claims it, then `SUCCESS`, or `RETURNED` after 30 days). A `reconciliation` entry gains a payout form: `payout: { batchId, itemId, status, amount }` as re-read with `GET /v1/payments/payouts-item/{id}`, and the matched result. `npm run reconcile` re-reads every executed payout whose last logged item status isn't final, and logs a reconciliation when it changed. The webhook handles `PAYMENT.PAYOUTS-ITEM.*` events after the usual signature check by re-reading the item named in the event (never trusting the body), once per event ID. A returned or failed payout still counts in the day's usage, the conservative side.
- **The ops agent is not an AI here.** Brief §5 item 15 asks for an ops agent that can pay a supplier, not for its intelligence, and Resolve is the reference AI agent. The ops agent is the stand-in agent CLI (`npm run agent`) over MCP with the ops key, choosing its key from the proposal file's `principal`. No AI is added to the money path.
Basis:
- Brief §5 item 15 ("An ops agent can pay a supplier through PayPal Payouts, but only to an allowlisted payee and only with step-up. The support agent can never pay out"), §8 (fail closed; what you approve is what executes; the agent never holds PayPal credentials; no AI in the decision path), §9 (Payments: direct REST so we control `PayPal-Request-Id`).
- Original brief §7 ("A separate ops-agent mandate allows payouts only to an allowlist, always with step_up"), §8 (`payee.allowlisted`: "The payout recipient is on the signed supplier list", source of truth "Mandate"), §9 (`paypal.payout`, `POST /v1/payments/payouts`), §12 ("`PayPal-Request-Id` = intent hash; `sender_batch_id` = intent ID for payouts"; "the support-agent and ops-agent mandates are separate"), §16 (A5 payee swap).
- PayPal Payouts v1, create batch payout (read 23 Oct 2026): request `sender_batch_header` and `items` (`recipient_type`, `amount { value, currency }`, `receiver`, `note`, `sender_item_id`), `PayPal-Request-Id` header, 201 `batch_header { payout_batch_id, batch_status }`; reused `sender_batch_id` within 30 days is rejected with a link to the original; 5xx retries with the same `sender_batch_id` are safe: https://developer.paypal.com/api/payments.payouts-batch/v1/payouts-post and https://developer.paypal.com/api/payouts/customize#prevent-duplicate-requests
- PayPal "Use Payouts API" (batch read with `items[].payout_item_id`, `transaction_status` such as `UNCLAIMED`, `SUCCESS`, `FAILED`, and `errors.name`): https://developer.paypal.com/api/payouts
- PayPal payouts webhook events (`PAYMENT.PAYOUTS-ITEM.SUCCEEDED`, `.UNCLAIMED`, `.FAILED`, `.RETURNED`, `.BLOCKED`, `.HELD`, each related to "Show payout item details"): https://developer.paypal.com/api/rest/webhooks/event-names/#batch-payouts
- ADRs 0019, 0026, 0027, 0028, 0032, 0033, 0035.
Consequences:
- Phase 17's mandate compiler targets the `payees` key too; the plain-English read-back names each payee.
- `EXECUTABLE_ACTIONS` gains `paypal.payout`. Tests that used a payout as "an action with no executor" switch to order capture, which stays `ACTION_UNAVAILABLE`.
- The execution-result and reconciliation schemas gain payout forms; every existing entry still reads.
- The name of PayPal's duplicate-batch error isn't in the docs read; the rail client recognises it by name or issue, and the `LIVE=1` check records the real one.
- A second payout on the same bill with a different amount or note is a new intent; the step-up card shows the reference, so the merchant sees it. A verifier for paid bills could come with the bench (phase 14).
- The live payout check spends sandbox balance only. Sandbox payouts to an address with no sandbox account end `UNCLAIMED`; `PAYPAL_LIVE_PAYEE_EMAIL` (optional) names a sandbox personal account for a `SUCCESS` run.
