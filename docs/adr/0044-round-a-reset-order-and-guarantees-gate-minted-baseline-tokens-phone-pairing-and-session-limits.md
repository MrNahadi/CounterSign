# 0044. Round A of phase 13: the reset replaces before it clears and reads work from the log, today's usage restarts with the log, the gate mints hosted baseline tokens, the phone pairs by QR, and each session is rate-limited

Status: accepted; amends ADRs 0041 (hosting), 0042 (the demo reset), 0043 (the start page and sign-in) and, for the hosted demo only, 0031 (baseline tokens)
Decided-by: autopilot (delegated), phase 13 design review round A, 31 Oct 2026, under brief §14 v1.4. Critical (`.ralph/egm/PROCESS.md`): it touches §8 non-negotiables (credential custody, per-session rate limits, fail closed), changes what can move money and how a reset treats the guarantees that stop it, adds a way to sign in, and changes what a judge sees. The `answerer` agent was asked first. It answered six of the seven questions and escalated the custody question (part 4); the Elephant decided that one, choosing the option that fails closed. The planner can't start a fresh Goldfish, so the counter-argument below is the Elephant's, written as the Design Critic would. Decided by brief §10 trade-offs 1 (fail closed, absolute) and 3 (the judge path works every time). The owner can overturn it (`.ralph/human.md`, Decided for you)
Question: Round A's reviewers found that a reset silently restarted guarantees that read the audit log, that clearing before replacing left a broken window, that in-process guards missed other processes, that the agent's host held a PayPal secret beside a vulnerable toolkit, that a phone couldn't reasonably sign in with a 44-character key, and that §8's per-session rate limit was missing from the phase that makes the demo public. What changes?
Decision:
1. **What a reset keeps and restarts.** The order check also replaces every seeded order whose capture any `execution.requested` names, whatever its outcome (an unreadable request replaces all 30), so no kept capture loses its duplicate history. The run cap carries over (ADR 0042). **Today's usage for the mandate's limits restarts with the log**, as on a fresh seed. Open step-ups are cleared, and an old card fails on its intent hash. A repeated payout still meets PayPal's refusal of a reused `sender_batch_id`, and any new payout needs a new approval. Late webhooks are logged as refunds nobody requested (ADR 0026).
2. **Work is read from the database, inside the lock.** The in-process execution counter and the `npm run reset` CLI are dropped. The reset refuses (409) while any run or draft is queued or running, while an `execution.requested` from the last 10 minutes has no result, and for one minute after a reset (entry 1's time). It checks once before the order check and again inside the lock. Every rail call gets a 30-second timeout, so an execution can't outlast the window. Every service sets `autoDeployTrigger: off`. The in-process single-flight flag stays.
3. **Replace before clearing.** The reset reads the captures and runs the seed for the orders to replace first. It clears the log and Resolve's tables only if every replacement exists; otherwise it answers 200 with `cleared: null`. Inside the lock it also refuses (409) if any run was queued since the reset began, because a baseline run leaves no log entry, or if a capture now in `seed_orders` is named by an execution request.
4. **On Render, Resolve holds no PayPal credential.** A baseline launch goes from the console to the gate's `POST /baseline/launch` (approver key). The gate mints one sandbox token and sends it with the scenario to Resolve over the private network. Resolve uses it for that one run, in memory only. Locally, Resolve still mints its own token when the PayPal variables are set (ADR 0031).
5. **The phone pairs by QR.** The start page asks the gate for a single-use pairing code (16 random bytes, valid 5 minutes, held as a hash in the gate's memory) and puts it in the QR code's URL fragment. The approvals page trades it through the console for the same cookie the sign-in sets. Pasting the key, and approving on the desktop, stay as fallbacks.
6. **The seed state's tickets are the three scenario files.** A reset leaves the inbox empty, with the scenarios one tap away; queuing them on every reset would spend AI runs. M-Pesa receipts join the seed and the reset in phase 18.
7. **Each session is rate-limited now.** Signing in sets a random `countersign_session` cookie. Each session may start 12 runs and 3 resets in any 10 minutes (429 past that). A key cookie without a session cookie must sign in again. The limiter is in memory on the console's one instance; phase 15 reuses it.
Basis:
- Brief §8 ("The agent never holds PayPal or Daraja credentials; only Countersign does"; "each session is rate-limited, and AI spend has a daily cap"; fail closed; sandbox only), §5 item 3 ("one tap on their phone"), §5 item 6, §5 item 8, §7 (seed state), §3 (five minutes), §12 (after a reset, the stalled-parcel claim executes a refund), §13, §14 (§8 is never delegated), §10 trade-offs 1 and 3.
- The answerer (31 Oct 2026). Part 1: inferred. The v3 mandate allows 5 refunds and 30000 minor units a day, so carrying usage over would step up beat 4 by about the third judge of a day. Part 2: researched. The rail client had no per-request timeout; `autoDeployTrigger` replaced `autoDeploy`; Render stops the old instance at least 60 seconds after the new one takes traffic. Part 3: inferred (ADR 0031: baseline money moves never reach the log). Part 4: escalated; sources conflict between §8 and ADRs 0011 and 0031. Part 5: inferred, medium confidence. Part 6: inferred. Part 7: stated.
- Code: `packages/verifiers/src/usage.ts` and `ledger.ts` (usage and duplicates come from the log), `packages/verifiers/src/capture.ts` (PayPal's refunded amount caps refunds), `packages/ledger/src/log.ts` (`seq` from the newest row), `apps/storefront/src/seed-run.ts` (per-order upsert), `apps/resolve-agent/src/baseline.ts` (an injected token issuer), `packages/db/src/runs.ts` and `drafts.ts` (the cap's counting rule).
- Render Blueprint spec (`autoDeployTrigger`, `diskSizeGB`), read 31 Oct 2026: https://render.com/docs/blueprint-spec ; Render deploys: https://render.com/docs/deploys
Goldfish argument (the Elephant writing as the Design Critic, since no fresh Goldfish could be started): "Restarting today's usage on every reset means anyone with the shared key can buy the agent fresh auto-allow headroom in a loop. That weakens the very limits the project exists to enforce, for the sake of a demo beat. The gate-minted token adds a second launch path, so baseline and protected launches no longer travel the same way, and the gate becomes a token vending machine on the public internet. A pairing code is a new credential, introduced in the same phase that first puts the demo online. A session limiter that anyone can reset by signing in again limits nothing. Build less: keep ADR 0031's minting, let judges paste the key, and leave rate limits to phase 15 as planned."
Answer: Usage restarts only for someone holding the approver key. That key can already approve any stepped-up amount, a reset is limited to once a minute and 3 per session in 10 minutes, and every amount is sandbox money from the seed buyers. Carrying usage over would break §12's post-reset beat 4 for later judges (trade-off 3), so the trade costs nothing that trade-off 1 protects. The token route mints only for the approver key, which can already start baseline runs, and it hands the token to Resolve, never back to the caller, so no key gains power. Leaving the secret on Resolve breaks a §8 line that is absolute. The pairing code is 128 bits, single-use, lives 5 minutes, is never logged, and gives the phone only what its holder's own browser already has; without it, the judge path's phone step is a 44-character paste inside five minutes. Re-signing-in does start a new session, but §8 asks for per-session limits and a daily cap together, and the cap is what bounds a scripted caller. §8 is never delegated (§14), and this phase is the one that makes the demo public. The arguments are close only on build effort, which is trade-off 6, a tie-breaker; the fail-closed options stand.
Consequences:
- ADR 0042's in-process execution count and `npm run reset` are gone; its "partial is reported" now applies only to the dispute sync after the clear.
- ADR 0041's Resolve service loses `PAYPAL_BASE_URL`, `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET`. The console gains `CONSOLE_PUBLIC_URL` (`sync: false`), the database a 5 GB disk, every service `autoDeployTrigger: off`, and the cron job a failing exit when either command fails. Merged work reaches Render only when the owner deploys.
- ADR 0043's guide step 4 says the code signs the phone in. The console gains the session cookie and its limits, and the pairing route. The gate gains `POST /baseline/launch`, `POST /approvals/pairing-codes` and `POST /approvals/pair`.
- `CONTEXT.md`'s Approver key, Seed state and Demo reset entries change with the build (phase 13 item 24). Phase 18 adds receipts to the seed and the reset. Phase 19's threat model records that a compromised toolkit child could read Resolve's environment (`DATABASE_URL`, `GEMINI_API_KEY`, the support-agent key).
- Pairing codes, session limits and the reset's single-flight flag live in memory, so the gate and the console stay at one instance; a deploy overlap fails them closed.
