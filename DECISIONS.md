- 2026-11-08 (agent, E1): The mandate compiler's Gemini answer holds only `limits`, `rules` and `left_out`. Code copies the id, principal, time zone and payee list from the current mandate, sets the version to the current one plus one, and always sets `fallback: deny`, so the model can't widen what the mandate covers or whom it pays (payees aren't editable through the compiler). The answer must then pass the gate's own `MandateSchema`. Anything that doesn't fit is refused with the check's first issue and never repaired. The read-back is written by code from the validated mandate (`src/mandate-readback.ts`), not by the model, so the merchant reads what the gate would enforce, including what the evaluation order does: a failed check denies, an over-cap amount or a passed daily limit holds, the strictest match wins, the fallback denies. Rules Gemini says it couldn't express come back in `leftOut` rather than being approximated. The current mandate is the support agent's v3 file, the one the gate loads, imported through a new `@countersign/mandate/fixtures/*.json` export. `POST /api/mandate/compile` uses the approvals sign-in, a per-session `compile` limit (6 in any 10 minutes) and a daily cap of 100 for the whole console, with 8,192 output tokens. It only returns the draft: nothing is signed, stored or sent to the gate. E1 has no page; E2 builds the page with the diff and signing.
- 2026-11-08 (agent, E2): The replay reads decisions from the gate's audit log, not from the bench results files. A results file keeps only the gate's answer to each money call, not the intent, verifier trace and usage a replay needs, and a demo reset clears the log between genuine cases. So "the frozen bench decisions" become whatever decisions the log holds under the mandate in force: bench runs, the demo and visitors all write there, and the page says what was replayed and what was skipped. The gate runs the replay (`POST /mandates/replay`, approver key only) through `ruleDecision`, the rule step `decide()` now shares, using each decision's own intent, trace and usage. It runs offline, with no PayPal, carrier or AI calls. If the draft requires a check the original decision never ran, that check reads as unknown, so the decision replays as a deny. Only decisions made under the base version's exact hash are replayed. A draft must be the next version of a mandate the gate holds, with the same principal, time zone and payees, because those shaped the recorded usage and payee checks; any other draft is refused. Signing (`POST /mandates/sign`) appends a `mandate.version` entry (ref `id@vN`) under the ledger's lock, holding the draft, its hash, and the base version and its hash. A stale base hash is refused (409). Signing the same draft again returns the existing entry, and different rules for a version that's already signed are refused (409). Signing doesn't put the version in force: the gate keeps deciding with the file it loaded at startup, so the bench's v3 and the demo beats stay as they are, and the page says so. Until the owner decides otherwise, only v4 can be signed, and a reset clears it. The diff is worked out on the server and returned with the compile answer, in the read-back's words. Moving a rule isn't a change, and a single action written as a list (as the compiler writes it) reads the same as the plain string. Replay and sign have no session limit: replay only reads, and each version can be signed only once.
