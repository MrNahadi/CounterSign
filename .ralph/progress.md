## T-003 (done)
- `@countersign/ledger` `ENTRY_TYPES` gains `execution.requested`, `execution.result`, `reconciliation`. `apps/gate/src/execution-log.ts` adds the zod payload schemas (`ExecutionRequestedPayloadSchema`, `ExecutionResultPayloadSchema`, `ReconciliationPayloadSchema`), writers that return `EntryInput`s and throw on an invalid payload (`executionRequestedEntry`, `executionResultEntry`, `reconciliationEntry`), and `readExecutionHistory(dbOrTx)` returning `{ known: true, executions }` or `{ known: false, seq, detail }`.
- Payload shapes: a request has `requestId` (must equal `intentHash`) and `replay: false, decisionSeq` or `replay: true, firstRequestSeq, proposal, proposalTruncated` (writer takes `replayOf: { firstRequestSeq, proposal }`, proposal text via `proposalText`). A result has `requestSeq`, `outcome`, `refund { id, status }`, optional `error { name, issues, debugId }`; no intent ID in the payload (it's the ref) and its time is the entry's `at`. A reconciliation has `source` (`webhook` needs `event { id, type }`), `refund { id, captureId, status, amount }`, `resultSeq` (nullable).
- Gotcha: "no later failed result" is read per intent: an intent counts unless its latest request-or-result entry is a `failed` result. So failed then replay (no result yet, or executed) counts again, fail closed. T-006: a replay past 6 hours that sends nothing should not write a replay `execution.requested` after a failed result, or the intent will block its capture again.
- Gotcha: the history is also unknown for a result naming a request of another intent or no request, a replay of no earlier request, or a ref that isn't the payload's intent ID. Pass `log.tx` from `withAuditLog` to read inside the deciding transaction.

## T-006 (done)
- `proposeRefund` now answers replays and executes: inside the transaction it normalizes the proposal, and if the intent has a first `execution.requested` (`readIntentTrail(tx, intentId)` in `execution-log.ts`, type `IntentRecord`) it isn't decided again. Executed: writes only a replay request, no rail call. Otherwise, within `REPLAY_WINDOW_MS` (6 h from the first request's `at`): replay request, then re-send. After that: a decision entry denying `DUPLICATE_REFUND` (decide()'s record with the decision overridden, `matchedRules: []`), no replay request. On allow, `refundCapture` is sent after commit and `execution.result` appended with `appendEntry`; its time comes from the optional `clock` input (defaults to the system clock, never used for deciding).
- Result type: `{ ok: true, replay: false, record, seqs, execution | null }` or `{ ok: true, replay: true, intentId, intentHash, firstRequestSeq, seqs: { request }, execution }`. `Execution` is `{ outcome, refund, error, resultSeq, resultProblem, sent }`; `sent: false` is the "Replayed, no new refund." case for T-007.
- Outcomes: COMPLETED/PENDING executed; FAILED/CANCELLED, HTTP 4xx and `invalid_request` (refused before any call) failed; network, 5xx, `invalid_response` and any non-`PayPalError` throw unknown. A result append that fails sets `resultProblem` (fixed text for a thrown DB error) instead of throwing, so the refund ID isn't lost.
- Fake sandbox gains `lostResponses` (throws after the call takes effect), `refundStatus`, and refunds now appear on the order's purchase unit. The no-AI test now covers the gate's decide/execute modules.
- Gotcha: a replay with no amount after a refund normalizes to a different amount (less left), so it's a new intent and is denied `DUPLICATE_REFUND`, not answered as a replay. Demo files give amounts.
