# Progress: phase 5, Kikapu storefront and seed (specs/features/05-storefront-and-seed)

## T-001 (done)
- `@countersign/rail-paypal` now has `createPayPalClient({ env, fetch?, sleep?, now? })` (sandbox guard, shared OAuth token cache, 401 re-auth once, safe retries) with `getOrder`, plus `parsePayPalEnv` (returns `missing` and `problems` for CLIs to name), `PayPalConfigError` and `PayPalError` (`kind`: http | network | invalid_response | invalid_request; `call` is kebab-case like `get-order`, `oauth-token`).
- Gotchas for T-002: the internal `send()` in `src/client.ts` already handles POST (`Prefer: return=representation`, `PayPal-Request-Id`, retried only when a request ID is given); add calls next to `getOrder` and schemas in `src/records.ts`. `PayPalCapture.orderId` is filled with the order's own ID for captures read inside an order; get capture should read `supplementary_data.related_ids.order_id`. Trackers split their ID at the first hyphen into `captureId` and `trackingNumber` (seed tracking numbers contain hyphens). `parseMoney` rejects zero amounts. Relative imports inside packages are extensionless. Test helper `packages/rail-paypal/test/fake-paypal.ts` serves fixtures with an injected fetch.

## T-002 (done)
- The client gained `createOrder(input)`, `captureOrder(orderId, { requestId })`, `addTracker(orderId, { requestId, captureId, trackingNumber, carrierName })` (all three return a `PayPalOrder`) and `getCapture(captureId)` (a `PayPalCapture` with `orderId` from `supplementary_data.related_ids`). Input types `CreateOrderInput`, `OrderItem`, `AddTrackerInput`, `PostOptions` are exported; inputs are zod-checked and refused as `invalid_request` naming the field, never the value.
- Gotchas: `createOrder` computes the amount and `item_total` from the items, so callers pass items only (`unitAmount: Money`, `quantity` a number). The vault ID is added to the client's scrub set, so errors never echo it. Wire amounts come from `toPayPalAmount` in `src/records.ts` (formatMoney with `$` and commas stripped, checked by a parseMoney round trip). The tracker body uses PayPal's `carrier_name_other` field; T-010's live check should confirm it. Test helpers `testClient`, `caught`, `expectNoSecrets` (now also checks `FAKE_VAULT_TOKEN`) and `exposed` live in `test/fake-paypal.ts`.

## T-004 (done)
- `@countersign/carrier-mock` exports `CarrierAdapter` (`getShipment(trackingNumber)` returning `ShipmentLookup`: `found` with a `Shipment`, `not_found`, or `unreadable` with a one-line `detail`), `createMockCarrier(store)`, `ShipmentStore` with `createDatabaseShipmentStore(db | tx)` (upsert on tracking number) and `createMemoryShipmentStore(map?)`, plus `ShipmentSchema`, `TrackingNumberSchema`, `checkShipment` and `InvalidShipmentError`. Tests in `packages/carrier-mock/test/carrier-mock.test.ts` run the same cases over both stores.
- Gotchas for T-006: the `Shipment` fields mirror the `carrier_shipments` row (`trackingNumber`, `carrierName`, `status`, `scanEvents`, `updatedAt`), and `updatedAt` is passed by the writer (no clock). The database store takes a transaction (`Queryable`), so write the shipment with `createDatabaseShipmentStore(tx).write(...)` inside the seed's transaction. Scan events must be in time order with offset timestamps, and the schema is strict, so extra keys make a row unreadable. A stored record whose tracking number differs from the key is unreadable. carrier-mock imports zod from the root without declaring it, as rail-paypal does.
