## Decided for you

- **Phase 4, audit-log format (ADR 0022):** one `audit_log` table, payloads stored as their hashed canonical text, an envelope hash, an append-only trigger (TRUNCATE allowed for the demo reset), raw proposals kept as JSON text, and `mandate.version` entries written once per version. A hash chain can't detect a cut-off tail, so `ledger verify` prints the head.
- **Phase 4, chain link rule:** a row's `prev_hash` passes if it matches the previous row's stored hash or, when that stored hash was edited, the hash recomputed from the previous row, so an edited row is reported once at its own `seq`. Overturn to link to the stored hash only.
- **Phase 4, append rejections:** besides the spec's codes, appends reject `BAD_REF` (a ref with a lone surrogate, a fail-closed backstop since IDs can't hold one) and `BAD_INPUT` (an entry of the wrong shape).
- **Phase 4, proposal text fallback:** a proposal `JSON.stringify` can't serialize is recorded as `String(proposal)`, or `""` if that throws too, so recording never fails on content; `recordDecision` throws on a mandate that differs from the decided one.
- **Phase 4, CLI wording:** counts are pluralised ("1 entry", "1 problem", "Applied 1 migration."), and `tail` prints "Last N entries of M." or "The audit log has no entries.".
- **Phase 4, database precedence:** `DATABASE_URL` wins over `--pglite <dir>` when both are given, and `--pglite` is then ignored silently. Overturn to refuse both together.
- **Phase 4, decide env loading:** `decide-main.ts` loads `.env.local` itself (only with `--record`, never overriding set variables), because a phase 3 test pins the `decide` script without `--env-file-if-exists`. Change the test and script together to match the other scripts.
- **Phase 5, seed state and carrier data (ADR 0023):** seeded orders and carrier shipments live in two Postgres tables (`seed_orders`, `carrier_shipments`); the shipment status is stored, never worked out from the clock; each seed run has a resumable run ID; and two seed buyers are required, so beat 3's `TICKET_NOT_FROM_PAYER` can fire. The carrier's scan dates are backdated from seeding and can precede PayPal's capture time; the carrier is labeled simulated.
- **Phase 5, storefront scope:** storefront sales are real and captured but get no tracker or carrier record, and the shop sells one product per order. The planner couldn't reach the answerer agent from its session, so it applied the answerer's rules itself; ADR 0024 (rail client, v6 checkout with the client ID) is marked researched.
- **Phase 6, executions and exactly-once (ADR 0026):** an execution is logged as a request before the PayPal call and a result after; anything not definitely refused counts as executed, so a crash blocks further refunds on that capture until reconciled; a replay of an executed intent makes no call, others re-send the same request ID within 6 hours only; refunds nobody requested are still logged. The planner again couldn't reach the answerer, so ADR 0025 (refund, disputes and webhook calls) is marked researched.
- **Phase 6, beat 3's KIK-1040:** denied `NO_MATCHING_RULE` rather than `TICKET_NOT_FROM_PAYER`, because the parcel is in transit and no rule covers a not-received claim on it, so it's denied before the payer is checked. The spec expected four `TICKET_NOT_FROM_PAYER` denials.
- **Phase 6, late replay:** a replay after the 6-hour window is logged as a `DUPLICATE_REFUND` decision entry, with no replay request written and nothing sent.
- **Phase 6, unreadable execution entry in the webhook:** an execution or reconciliation entry whose payload can't be read makes the webhook answer 503 (so PayPal redelivers) and write nothing.
- **Phase 6, live disputes check (validator):** the sandbox answers a disputes lookup for a capture the merchant doesn't hold with 400 `INVALID_REQUEST`, not an empty list, so the live check now expects that error for a made-up ID (the gate leaves the disputes snapshot out, failing closed) and checks a real capture's empty list in the vault refund test.
- **Phase 6, executed then refused (validator):** an intent whose result once said `executed` stays in the execution history even if a later re-send of it is refused, because money moved. requirements.md's "no later failed result" read literally would have dropped it and let a second intent on that capture through `ledger.not_duplicate`.
- **Phase 6, replay of a refused intent (validator):** a refused intent stops counting against its capture, so another intent may execute on it. A later replay of the refused one is then denied `DUPLICATE_REFUND` (logged as a decision, nothing sent) instead of being re-sent within the 6 hours as ADR 0026 reads, so the capture can't be refunded twice. With nothing else executed on the capture, it's still re-sent.
- **Phase 7, intent targets (ADR 0027):** each guarded action hashes its own target (dispute, invoice, order, payee) plus the parameters that execute, such as a note or offer type; refund hashes are unchanged; only refunds need a ticket; a target record that can't be read denies `TARGET_UNKNOWN`. The planner couldn't reach the answerer agent, so it applied the answerer's rules itself.
- **Phase 7, MCP surface (ADR 0028):** agents authenticate with a principal key as a bearer token from `COUNTERSIGN_SUPPORT_AGENT_KEY`; the gate uses the MCP SDK's low-level `Server` (amending ADR 0001) so invalid calls are still logged; denials are answers, not MCP errors; only refunds execute, and an allow for anything else is denied `ACTION_UNAVAILABLE`; read-only tools are served by our own PayPal client, not by spawning PayPal's toolkit.
- **Phase 7, ticket store (ADR 0029):** tickets live in a write-once `tickets` table that Resolve writes and the gate reads by the ID the agent names, so the agent can't choose the sender a verifier sees.
- **Phase 7, db links mandate (builder):** `@countersign/db` now depends on `@countersign/mandate` to reuse the shared timestamp rule for a ticket's received time, although plan.md said no new workspace links.
- **Phase 7, simulated ticket time (builder):** a simulated ticket's received time is the run's now(), not a time from the proposal file.
- **Phase 7, `seed_order` (builder):** proposal files gained a `seed_order` field, allowed only on `pay_order`, so a demo proposal names a seeded order by its order number (such as KIK-1037) and the CLI looks up its PayPal order ID.
- **Phase 7, live 404s (builder):** the builder couldn't confirm that the sandbox answers 404 for a made-up dispute and invoice ID. The validator ran `LIVE=1` on 2026-10-18 and both answered 404 as `PayPalError`s.
- **Phase 8, Resolve's intake and runs (ADR 0030):** both channels are simulated (no real email in or out; replies are stored and shown); resolve-agent is the one service that takes messages in and the console reaches it only through server routes; tickets gain a thread ID; photos (JPEG, PNG, WebP, 3 per message, 2 MB each) live in a write-once `ticket_attachments` table; each run is a row in `agent_runs`; runs go one at a time; interrupted runs are marked failed and never rerun; a daily run cap (default 200) is the only AI-cost guard until phase 15. The planner had no way to start the answerer agent, so it applied the answerer's rules itself.
- **Phase 8, Resolve's two modes (ADR 0031):** one fixed system instruction, config and user turn for both modes; a local read-only `find_order` tool (the shop's order book, never the payer's email) in both modes, because PayPal's tools can't look up `KIK-1042`; baseline spawns PayPal's server per run with a fresh sandbox token; at most 8 model calls and 12 tool calls a run; a run is retried on the fallback model only if it failed for quota before any tool call. Overturn the prompt wording in requirements.md if it reads as tuned for either mode.
- **Phase 9, approvals (ADR 0032):** a step-up is its decision entry (ID = its `seq`), and its states are worked out from the log and the clock; the merchant signs in with `COUNTERSIGN_APPROVER_KEY`, kept in an HttpOnly cookie, and a principal key never works there; every tap, rejections included, is an `approval` entry; an approval executes the stored intent and never re-decides; a deny closes every earlier step-up of that intent. The planner had no way to start the answerer agent, so it applied the answerer's rules itself.
- **Phase 9, executors and invoice sends (ADR 0033):** refunds and invoice sends share one executor per action; PayPal's invoice send takes no request ID, so it's sent at most once and never retried or re-sent; executed invoice sends count in today's usage (the conservative side). Overturn if invoices shouldn't count against the refund limits.
- **Phase 9, QR library:** `uqr` 0.1.3 (no dependencies) rather than `qrcode` 1.5.4, so the console draws the QR with Graphite tokens.
- **Phase 9, re-proposed invoice send (builder):** under a mandate that allows invoice sends outright, proposing the same allowed invoice intent again answers `allowed` with no second send, since no reason code says "already sent". The shipped mandate steps invoice sends up, so this isn't reachable in the demo. Overturn to deny it instead.
- **Phase 10, claims vs records and the audit console (ADR 0034):** the two columns are built once in the gate and shown on the phone card, the console and the `audit` CLI; the verdict (Matches, Contradicts, Passes, Fails, No record, Not used) comes from a fixed table over the verifier's result, and the message text is always "Not used", never judged; the agent response never carries records (they hold the payer's email), so Resolve's inbox links each call to its decision page; the console reads the log through a read-only gate API opened by the approver key (so that key now also reads the audit log); unreadable entries are listed, not hidden; evidence exports are whole rows that `ledger check-export` re-hashes; the decision list is a Graphite table, not AG Grid. The planner had no way to start the answerer agent, so it applied the answerer's rules itself.
- **Phase 11, dispute evidence (ADR 0035):** a dispute arrives as a new `dispute.received` audit-log entry (webhook or `npm run disputes -- sync`), and the gate nudges Resolve; the gate builds the evidence pack without AI and stores the PDF and export JSON write-once, and the PDF's SHA-256 is inside the intent, so you approve those exact bytes; a new non-guarded extension, `prepare_dispute_evidence`, hands the agent the facts without payer emails or ticket text; Resolve's drafter makes one Gemini call that writes only the notes, and code sets evidence types, tracking numbers and documents, with a fixed template when Gemini is unavailable; accept claim, make offer and provide evidence all execute now, sent once with no request ID, and count in today's usage. The new dependency is `pdf-lib` 1.17.1. The planner had no way to start the answerer agent, so it applied the answerer's rules itself.
- **Phase 11, documents optional (builder):** `document_ids` is optional on `provide_dispute_evidence`, so a submission without documents still normalizes and older hashes stay unchanged; the drafter always sends the PDF. Say if it should be required.
- **Phase 11, tracking numbers per item (builder):** the proposal schema and rail client allow 100 tracking numbers per evidence item, but PayPal takes at most 10; over 10 gets a 4xx and is recorded `failed`, so it fails closed. A cap in the proposal schema would refuse it before sending.
- **Phase 11, drafts over the daily cap (answerer):** a draft past the run cap is stored `not_run`/`daily_cap`, as requirements.md says, and isn't drafted later; ADR 0035 instead says over-cap drafts use the template. Say which you want.
- **Phase 11, a changed document on a card (builder):** a card whose document no longer matches still offers Approve; approving records `failed`/`DOCUMENT_CHANGED` and sends nothing. The gate could mark the card `cannot_execute` instead.
- **Phase 11, Disputes page rows (builder):** the page lists Resolve's drafts, so a dispute whose nudge never reached Resolve isn't shown until someone runs `npm run resolve -- dispute <id>`. Showing every dispute PayPal opened would also need the gate's `dispute.received` entries.
- **Phase 11, carrier on evidence (answerer, ADR 0036):** tracking numbers go to PayPal as carrier `OTHER` with the fixed name "Carrier (simulated)".
- **Phase 12, ops payouts (ADR 0039):** the ops agent gets its own key and mandate; the supplier list lives in that signed mandate (two illustrative `example.com` suppliers); every payout names the supplier's bill reference, so one bill is paid at most once, and is USD only; payouts go out once with the intent hash as request ID and the intent ID as batch ID, and reconcile by poll and the payouts webhook; the ops agent is the stand-in CLI, not an AI. The planner had no way to start the answerer agent, so it applied the answerer's rules itself.
- **Phase 12, reason codes join late (ADR 0040, builder):** a reason code joins the catalog in the ticket whose decision case first reaches it, so `PAYEE_NOT_ALLOWLISTED` moved from T-001 to T-004 and T-001's acceptance was reworded. Check you're happy with the changed ticket split.
- **Phase 12, webhook ref for an unknown payout (builder):** a payouts webhook item is linked to its intent whenever the log has a payout request for its `sender_batch_id`, so a payout whose result was `unknown` gets a reconciliation with its ref set and `resultSeq` null. Narrow `payoutMatch` in `apps/gate/src/webhook.ts` if you meant executed payouts only.
- **Phase 12, payout replay (validator):** the sandbox doesn't replay a payout by `PayPal-Request-Id`; the same request again answers 400 `USER_BUSINESS_ERROR` "Batch with given sender_batch_id already exists". The live check now accepts that refusal, and a client retry after a lost answer is recorded `unknown`, never a second payout. requirements.md's "replay answering the same batch" doesn't hold.
- **Phase 12, missing ticket in claims vs records (validator):** "Ticket <id> isn't in the ticket store" now counts as asserting nothing, so beside a passing check it reads Passes, not Matches. This showed on decisions recorded from case files (`npm run decide -- … --record`), whose verifiers read the case's ticket snapshot, which the store doesn't hold; those snapshots still name "Ticket store" as their source.
- **Phase 13, hosting on Render (ADR 0041):** one `render.yaml` on the smallest paid plans in Oregon; resolve-agent private and Postgres reachable only inside Render; services find each other through Render's `hostport`, turned into the existing URL variables in each start command; Render generates the support, ops and approver keys on the gate; a reconcile cron every 10 minutes also re-syncs disputes; one instance per service. The planner couldn't start the answerer or a Goldfish sub-agent, so it applied the answerer's rules and wrote its own counter-argument in each phase 13 ADR; round A's Design Critic reviews them.
- **Phase 13, the demo reset (ADR 0042):** the gate runs it, only with `COUNTERSIGN_DEMO_RESET=on` and the approver key, never while Resolve or an execution is mid-flight; it clears the audit log, tickets, attachments, runs, drafts and evidence documents in one locked transaction and starts the new log with a `demo.reset` entry naming the old head; it replaces only the seeded orders whose captures aren't `COMPLETED` (refining ADR 0023's fresh-run-or-reuse), records open disputes again, and carries the day's run count over, so a reset never buys more AI calls. The seed code moves to a new `@countersign/seed` package. A judge with the key can reset during another judge's session; phase 15's limits are the follow-up.
- **Phase 13, judges' access (ADR 0043):** the console opens on a start page (guide, three-scenario launcher, phone code, reset); every console route to Resolve, the inbox and the customer chat included, now needs the approver sign-in; on the hosted demo baseline mode runs only the attack-email scenario (`RESOLVE_BASELINE=scenarios`), so visitor text never reaches PayPal's toolkit.
